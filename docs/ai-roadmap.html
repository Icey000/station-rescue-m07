现有资源：美术够用，AI 接口还要补

机器人与动作 · 可复用

移动、滚动与转头、冲刺、碰撞、触电失速已存在。PlayerMotor 提供移动输入与冲刺请求；AI 可以操控现在这一个 M-07。

物体与完整任务 · 可复用

两种电芯、充电架、回收柜、发电机、三个随机港口、通电动画与登船交互已组成“识别 → 搬运 → 安装 → 撤离”。

美术素材 · 足够起步

工程已导入 Kenney 的发电机、气闸、管道、平台、栏杆、货船等模型。门禁卡、符号牌、控制台可以先用现有模型与简单图标制作。

Python 通信 · 尚未接入

Packages/manifest.json 中没有 ML-Agents；没有实验入口、外部动作适配器和模型运行器。现有接口是基础，整条通信链仍需要实现。

截图 · 有测试先例，缺观察通道

Windows 验证程序能捕获实际屏幕。HUD 使用 ScreenSpaceOverlay；接相机传感器时必须验证收到的图像确实包含约定的任务与交互信息。

重开与随机性 · 有基础，缺实验协议

当前重开通过重新加载 Game 场景；StationPlan.Create(seed) 能固定需求、电芯摆放与港口。还需外部任务配置、新局编号、完整重置和动作日志。

随机不等于关卡已经丰富：目前随机的是需求电芯、两个电芯所在的架子和出口。按 2 种需求 × 3 个出口 × 4 个蓝电芯位置 × 3 个橙电芯位置，这四项最多形成 72 种组合，底层墙体和道路相同。不同 seed 可能产生相同组合，D 不能仅按 seed 数字拆测试集。

看看当前画面，为什么它还不足以测试记忆？

建议的新任务：先在入口看见本局“圆形符号对应蓝电芯”的随机映射，进入另一个房间后只看见符号插槽，必须回忆或花成本返回确认。线索要离开画面，HUD 也不能继续写答案。这个任务当前尚未实现。

检查依据：Assets/Scripts 下的 PlayerMotor、HumanInput、PlayerInteraction、RepairGame、StationPlan、GameFlow、GameHud、StationSmokeRun；Packages/manifest.json；Assets/ThirdParty/KenneySpaceKit；既有 Windows 截图。现有自动验收部分使用内部坐标与导航辅助，是游戏测试，不能算视觉 AI 已经会玩。

B：把游戏接成可控的实验环境

B 的成果：Python 能可靠地操作 M-07、看到画面并开始下一局。先由固定脚本发出“向前走一小段、停、冲刺一次、交互一次”，检查通信、控制、截图和重置。

用现有游戏具体做一次

  1. Python 选择任务配置与 seed，启动实验模式；Unity 生成明确的新局。
  2. Python 收到当前 RGB 图像。人只看收到的图，也能认出机器人、电芯和约定的任务信息。
  3. Python 发出合法动作，Unity 经现有控制器执行短时间，再返回更新的图像。
  4. 重复几次，再重开。机器人、门、电芯、速度、冷却、粒子、计时和待执行动作恢复到新局状态。

动作最初按 V3 分成三个选择：停/前/后/左/右、是否冲刺、是否交互。方向保持短时间；冲刺和交互每条指令只触发一次。按 E 与 AI 交互仍使用同一套游戏规则。

B1–B8：实际要做的 8 步
  1. B1 · 隔离通信环境：核对 C# 包与 Python SDK 的兼容组合并锁定版本。优先装通信依赖，确认能导入 UnityEnvironment、Unity 无新编译错误。
  2. B2 · 官方示例排错：有安装故障时，用官方示例验证工具链，再回到自己的游戏。示例承担排错，不计为自己的主要成果。
  3. B3 · 实验入口与适配：新增 Lab 模式，沿用玩法规则。人工输入与外部输入互斥，否则 HumanInput.Update 会覆盖 AI 移动。物理步进只保留一个执行者。
  4. B4 · 动作与时间：实现三组离散动作，明确一次动作执行多少模拟时间。给新局和动作编号；重复、过期或上一局指令不能再次执行。
  5. B5 · 视觉观察：以 RGB 512×512 作为初始候选，检查方向、时效、文字与物体辨识度，再调整构图和分辨率。禁止把目标坐标、对象答案或隐藏状态当作视觉输入。
  6. B6 · 带配置重置：做本项目的 reset(task_config, seed) 包装，恢复全部状态并等待新局准备好。该签名是我们的协议，不是 SDK 原生接口。
  7. B7 · 日志与裁判隔离：保存每步图片、动作、模拟时间、真实事件和结束原因。策略只收到约定观察；内部完成状态留给独立裁判。
  8. B8 · 无模型压力测试：多局运行固定与随机动作，检查重置、重复指令和截图对应关系。随机策略不要求通关，接口错误必须能解释。

B 完成标准：一个 Python 入口能连续开局、发动作、得到新画面与结束状态；日志能逐步复查，人工模式仍能独立运行。

通信底座优先参考 Unity ML-Agents Low-Level API。它提供动作、观察和环境重置；一次 step 推进到智能体再次请求决策，不保证等于一个渲染帧。安装前依据 官方安装说明 核对实际发布版本，不仅按 Git 标签猜兼容性。

C：让视觉模型根据画面决定怎么走

C 的成果：AI 自己玩出一段可以复查的任务过程。给它画面和任务：“找到需要的电芯，安装后去亮起的港口登船。”模型选择动作，Unity 执行，再把新画面交回模型。

  1. 1 · 看截图与允许的任务信息
  2. 2 · 想判断当前子目标
  3. 3 · 做输出有限动作
  4. 4 · 核对新画面与真实结果

例如：看见蓝电芯 → 小步走近 → 看见拾取提示后交互 → 携带物变化 → 朝发电机走 → 安装 → 等待通电 → 找绿色支路和开启港口 → 靠近并登船。看错、走偏或冲过头，也要留下过程。这些是待验证行为，不是已实现的演示。

C1–C6：实际要做的 6 步
  1. C1 · 假模型：先返回固定动作，验证缺字段、多字段、非法方向、超时和旧局回应会被拒绝。模型输出只作动作数据，不当作代码执行。
  2. C2 · 一个真实视觉模型：接收图片、任务与有限历史，输出统一动作。密钥放环境变量；记录模型与提示版本，换模型时不改 Unity。
  3. C3 · 最小闭环：先验证一个房间、一个明显目标的看图移动，再做拾取、安装与完整救援。先跑小批任务，保留失败，不用一条成功录像代替测试。
  4. C4 · 局内记忆：记录“哪一帧看见电芯、尝试过什么、下一目标是什么”。记忆来自画面或自己的动作；新局清空，不从 Unity 内部读取答案。
  5. C5 · 预算与恢复：限制动作、调用、费用、超时与重试。模型服务断连时能停下来；重开后不能执行迟到回应。
  6. C6 · 冻结 Demo：固定游戏、相机、动作、提示与记忆格式。交付运行入口、完整轨迹和成功及失败示例，作为 D 的比较底座。

时间模式要说明：入门时建议模型思考期间暂停模拟，拿到动作再推进，这测按步骤决策。以后可另做实时模式，让放电周期继续运行。两种结果分别记录，服务等待时间不能混成机器人决策能力。

C 完成标准：模型通过实际图像输出合法动作，完成最小任务闭环；成功与失败可重放，费用与超时受控。完整任务成功率由实际试验填写。

可以借鉴作者项目 GamingAgent 的游戏适配、模型运行与评测组织，并按 MIT 授权 复用合适代码；我们的 Unity 接口仍需适配。lmgame-Bench 论文 讨论感知、记忆、提示变化与游戏评测可靠性，可帮助设计实验。

D：证明哪些设计有效，花了多少代价

D 的成果：可复现的实验和有证据的结论。同一个模型，在相同任务条件下，比较加入记忆、改变重规划时机前后，成功率、动作数、调用次数和费用怎么变化。结论可以是没有改善，也可以是某类任务改善、另一类退步。

先做三个任务族

  1. 导航：找亮起的目标港口，避开箱子和放电区，到达后交互。机器人、碰撞、港口和危险区可复用；需任务配置与独立验收。
  2. 前置条件：当前“正确电芯 → 启动发电机 → 开港口 → 登船”提供基础。更复杂版本可做“门禁卡 → 维修间 → 电芯 → 安装 → 撤离”，增加门禁卡与锁门逻辑。
  3. 记忆：先看本局随机符号与电芯对应关系，再去另一房间选择。需线索牌、局部观察与线索离开视野的条件；HUD 只保留任务目的，返回查看有明确成本或限制。

第三类是当前最明显的缺口。只删目标文字，却让线索牌永远出现在整幅俯视画面里，仍不足以检验记忆。改变信息条件时要保证可解，不能靠藏掉所有提示增加难度。

比较的三组是什么？

  • P0 · 当前图像：每次使用当前图像与允许的任务说明，不保留跨步记忆；按固定节奏决策。
  • P1 · 有局内记忆：加入有长度上限、来自既往观察的记忆，其余条件和决策节奏保持一致。P1 与 P0 比较记忆的作用。
  • P2 · 有记忆，按观察到的事件重规划：复用 P1 的记忆，看到拾取成功、门开启、路线受阻等事件时更新计划。P2 与 P1 比较调度的作用；事件来自合法观察，不能读取隐藏状态替 AI 判断。

“记忆”是运行器保留并交给模型的历史信息，不是重新训练模型参数。三组用同一模型、同一套任务和动作、相同上限预算；P2 不预设一定更好。

D1–D6：实际要做的 6 步
  1. D1 · 三个任务族：实现导航、前置条件与记忆的实际规则，保证需要不同能力且存在合法完成路径。
  2. D2 · 划分关卡：开发集用于调试，验证集用于选择方案，最终测试集封存。按布局和任务规则排重；相同布局的不同 seed 不能散到两侧。
  3. D3 · 控制条件：冻结模型、提示、动作与预算；分别比较 P1-P0 和 P2-P1，明确机制差异，不提前填提升百分比。
  4. D4 · 批量运行：先小规模检查流程，再按预算扩展。相同任务配置配对比较并重复，记录成功率、动作、调用、tokens、费用、模拟时间和真实等待时间。
  5. D5 · 失败分析：用轨迹区分看错、忘记、顺序错误、移动失控、通信故障、环境问题与无法判断。保留全部尝试；服务错误单独报告，不能偷偷删掉。
  6. D6 · 可复现成果：提供任务配置、运行方法、日志与结果、限制和代表录像。每个功能与数字对应证据；研究版继续保留课程 A1.0。

D 完成标准：别人能按方法运行比较，找到结论对应的记录，并理解适用任务、条件与费用限制。它是一项实验成果，不要求 AI 每局都通关。

现在实际怎么起步？

下一项技术工作建议是 B 的最小桥接：Python 启动同一游戏 → 收到一张带必要信息的真实图 → 发出一次向前移动 → 收到变化后的图 → 重开并确认状态干净。先验证这一小环，再做完整任务控制。

你决定研究问题、成功条件和关卡是否认可；我可以落实 Unity 适配、Python 运行器、记录与测试。做到 C 时再确定模型、凭据和调用预算。老师对 A 作业的反馈可继续记录，不需为 B-D 先重做美术。

B-D 是项目 V3 的研究路线。课程 A 的作业要求、公开 Git 链接与复盘提交仍按老师 PDF 单独核对；目前没有证据表明老师额外要求 B-D。
