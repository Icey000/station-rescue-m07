# Game design brief

把玩家的构思转成可以实现、可以验收的需求。用户输入和已授权的工作范围优先；本次示例不约束下一款游戏的题材、按键或交互方式。

## 根据请求选择输出

- 构思阶段：整理玩法、关键物体、交互前提与验收；不要把讨论当成实现或发布授权。
- 已要求实现：读取现有工程并直接推进，保留用户已认可行为与已有改动。
- 经验复用：提炼实际反馈、原因与检查遗漏，并映射到下一份需求中的可填写项。相关例子见 [停电救援经验](references/station-rescue-lessons.md)。
- 仅修 Bug：复现、定位、最小相关修复、回归，不重做整个玩法。

## 需求里最容易漏掉的契约

1. 核心循环用玩家动作写；定义成功、失败、恢复与这轮范围。区别课程硬要求、用户选择、现状和模型假设。
2. 重要物体写身份、用途、可识别形状、交互前提、动作与反馈。参考图说明借鉴层次，图中文字不自动增加功能。
3. 明确靠近/碰撞/按键/点击/按住/自动的触发方式，说明拒绝、重复与同时输入。按用户选择设计，手动交互不是所有游戏的规定。
4. 对每个状态及过渡同时定义动作权限和表现；考虑暂停、重开与中途失败。可见反馈应与实际规则一致。
5. 状态变化会扩展可达空间。检查开门后、平台、边缘及回程的物理支撑；若掉落是玩法，说明后果与恢复，避免意外软锁。
6. 常驻信息只承担当前决策，细节放简报/帮助，附近再提示动作；结合形状、动画与声音而非只改颜色。
7. 验收写“前提 → 输入 → 预期”。覆盖正常、无操作、错误、重复、越界、暂停、重开与完整移动流程；报告实际结果和未覆盖内容，检查数量不能代替行为覆盖。

关键信息缺失时指出具体缺口，并继续不依赖该答案的工作。避免用大量问题阻塞已明确的实现；可把普通实现选择列为假设。

用户要 Prompt 时，输出已确定要求、待确认项、本轮阶段和交付/验收。用户要填表工具时，支持空白项目、可修改示例、导出/导入及缺项提示；不能在新项目里偷偷继承示例参数。发布、公开仓库、发送和付费不从设计需求推导额外权限。
